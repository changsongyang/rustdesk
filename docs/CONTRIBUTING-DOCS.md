# RustDesk 文档维护规范

## 1. 概述

本规范旨在确保 RustDesk 项目文档的质量、一致性和时效性，为文档贡献者提供清晰的指南。

## 2. 文档结构

### 2.1 目录结构

```
docs/
├── DEVELOPMENT.md    # 开发手册
├── BUILD.md          # 构建手册
├── OPS.md            # 运维手册
├── DEPLOYMENT.md     # 部署手册
├── README.md         # 文档索引
└── CONTRIBUTING-DOCS.md  # 本规范
```

### 2.2 文档模板

每个手册应遵循以下结构：

```markdown
# 文档标题

## 目录

1. [章节1](#1-章节1)
2. [章节2](#2-章节2)
...

---

## 1. 章节1

### 1.1 子章节

内容...

---

## 更新日志

### vX.Y.Z (YYYY-MM-DD)
- 变更说明
```

## 3. 编写规范

### 3.1 格式规范

- 使用 Markdown 格式编写
- 代码块使用语言标识（如 `bash`, `rust`, `yaml`）
- 表格用于展示结构化数据
- 代码示例应可复制、可执行

### 3.2 命名规范

- 文件名使用大写英文，用连字符分隔（如 `DEVELOPMENT.md`）
- 标题使用 `#`, `##`, `###` 层级结构
- 代码中的变量、函数名使用反引号括起来

### 3.3 语言规范

- 使用中文编写
- 术语保持一致性
- 避免使用口语化表达
- 保持客观、专业的语气

## 4. 更新流程

### 4.1 提交流程

```
1. Fork 仓库
2. 创建文档分支 (docs/feature-name)
3. 修改/创建文档
4. 提交 PR
5. 审核通过后合并
```

### 4.2 提交消息格式

```
docs(module): 描述变更

详细说明（可选）
```

**示例**:
```
docs(development): 添加 API 接口文档章节
docs(build): 修复编译步骤中的错误
```

### 4.3 审核机制

- PR 需要至少 1 位审核人批准
- 审核内容包括：
  - 内容准确性
  - 格式规范性
  - 语言通顺性
  - 技术正确性

## 5. 版本管理

### 5.1 版本号规则

采用 Semantic Versioning：

```
MAJOR.MINOR.PATCH
```

- **MAJOR**: 重大结构变更
- **MINOR**: 新增章节或功能
- **PATCH**: 修复错误或小改进

### 5.2 更新日志

每个文档应包含更新日志章节，记录重要变更：

```markdown
## 更新日志

### v1.1.0 (2024-02-15)
- 新增 API 接口文档章节
- 更新技术栈版本信息

### v1.0.0 (2024-01-01)
- 初始版本发布
```

## 6. 最佳实践

### 6.1 内容质量

- 确保信息准确、最新
- 提供可操作的步骤
- 包含代码示例和配置文件
- 使用图表辅助说明

### 6.2 可维护性

- 保持文档简洁明了
- 使用链接进行跨文档引用
- 避免重复内容
- 定期审查和更新

### 6.3 协作

- 关注相关 Issue 和 PR
- 及时响应文档反馈
- 参与文档审查

## 8. 常见问题

### Q1: 文档与代码不同步怎么办？

**A**: 提交代码变更时，同步更新相关文档，并在 PR 中注明文档变更。

### Q2: 如何处理过时的文档？

**A**: 定期审查文档（建议每季度一次），标记过时内容并及时更新。

### Q3: 文档冲突如何解决？

**A**: 使用 Git 合并工具解决冲突，必要时与相关作者沟通。
